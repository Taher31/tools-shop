# فروشگاه ابزار (Toolshop)

پلتفرم فروش آنلاین ابزارآلات برای بازار ایران: فروشگاه فارسی و راست‌به‌چپ، پنل مدیریت، انبار و موجودی چندانباره، سفارش و پرداخت، موتور جست‌وجوی فارسی و سطح دسترسی دقیق. معماری «مونولیت ماژولار» است: یک API با ماژول‌های مستقل و یک اپ Next.js. پایگاه‌داده فروشگاه تنها مرجع داده است و سرویس‌های بیرونی (درگاه پرداخت، ترب، دیجی‌کالا و …) فقط از راه آداپتر به آن وصل می‌شوند.

> **وضعیت:** فاز ۱ پیاده‌سازی و آزموده شده است. نام و برند نهایی هنوز تعیین نشده؛ همه نام‌ها، رنگ‌ها، برندهای کالا و داده‌های نمونه placeholder هستند و از پنل یا فایل تم قابل تغییرند.

## امکانات فاز ۱

**فروشگاه (RTL، واکنش‌گرا):** صفحه اصلی، همه کالاها، دسته‌بندی سلسله‌مراتبی، برند، جست‌وجو با فیلتر و مرتب‌سازی، صفحه محصول (گالری، تنوع‌ها، مشخصات فنی، نظرات و پرسش‌وپاسخ، کالاهای مرتبط و لوازم جانبی)، مقایسه، علاقه‌مندی، سبد خرید مهمان و کاربر (ادغام پس از ورود)، کد تخفیف، تسویه حساب با آدرس و روش ارسال، درگاه آزمایشی، نتیجه پرداخت، حساب کاربری (پروفایل، سفارش‌ها و جزئیات و لغو، آدرس‌ها، امنیت)، درباره ما، تماس، قوانین، مرجوعی، ارسال، گارانتی، حریم خصوصی، سوالات متداول. نمادهای اعتماد (اینماد و مجوزها) و اطلاعات حقوقی از تنظیمات پنل در فوتر نمایش داده می‌شوند.

**پنل مدیریت:** داشبورد فروش (تقویم و ساعت تهران)، سفارش‌ها و تغییر وضعیت با تاریخچه، پرداخت‌ها و بازپرداخت، مشتریان، محصولات با ویژگی‌های پویا و تنوع‌ها و تصاویر، دسته‌بندی‌ها و تخصیص ویژگی، برندها، ویژگی‌ها، موجودی و اسناد انبار و انتقال بین انبارها، انبارها، کوپن‌ها، روش‌های ارسال، نظرات، پرسش‌ها، صفحات محتوایی و FAQ، کاربران و نقش‌ها، تنظیمات، گزارش ممیزی (Audit Log). منوی هر کاربر فقط بخش‌های مجاز او را نشان می‌دهد و API هم مستقلاً هر درخواست را مجوزسنجی می‌کند.

**هسته تجاری:** قیمت‌گذاری فقط در بک‌اند، رزرو موجودی بدون فروش مازاد، ماشین حالت سفارش، رابط درگاه پرداخت مستقل از PSP، رویدادهای دامنه با الگوی Outbox، نمایه‌سازی جست‌وجو در صف، ممیزی تغییرات با مقدار قبل/بعد.

معیارهای «Definition of Done» فاز ۱ همگی برقرارند: اجرای محلی، مایگریشن و seed، ورود ادمین، CRUD محصول و دسته‌بندی، ویژگی‌ها، مدیریت موجودی، نمایش و جست‌وجوی محصول، سبد، تسویه، پرداخت آزمایشی، مشاهده سفارش در پنل، اعمال مجوزها، Docker، و build بدون خطا (به‌اضافه lint، typecheck و ۹۶ آزمون خودکار).

## راه‌اندازی محلی

پیش‌نیازها: Node.js 22 (فایل `.nvmrc`)، pnpm 10 (از طریق `corepack enable`) و Docker برای سرویس‌های زیرساخت. اگر PostgreSQL 16، Redis 7 و Meilisearch را جداگانه نصب کرده‌اید، Docker لازم نیست؛ فقط آدرس‌ها را در `.env` تنظیم کنید.

```bash
cp .env.example .env          # یک فایل .env در ریشه برای همه اپ‌ها
corepack enable
pnpm install
pnpm infra:up                 # PostgreSQL، Redis و Meilisearch با docker compose
pnpm build                    # ساخت پکیج‌ها و تولید کلاینت Prisma
pnpm db:deploy                # اعمال مایگریشن‌ها
pnpm db:seed                  # داده نمونه، نقش‌ها و کاربران آزمایشی
pnpm dev                      # API روی :4000 و وب روی :3000 (حالت watch)
```

- فروشگاه: <http://localhost:3000> — پنل مدیریت: <http://localhost:3000/admin>
- API: <http://localhost:4000/api/v1> — سلامت: `/api/v1/health/live` و `/api/v1/health`
- اپ وب درخواست‌های `/api/v1/*` و `/uploads/*` را به API پراکسی می‌کند تا کوکی‌ها هم‌مبدأ باشند.
- نمایه جست‌وجو اگر خالی باشد هنگام بالا آمدن API خودکار ساخته می‌شود. برای بازسازی کامل (مثلاً بعد از تغییر مترادف‌ها): `pnpm search:reindex` (بعد از `pnpm build`).
- برای تغییر schema: `pnpm db:migrate` (ایجاد مایگریشن جدید در حالت توسعه).

## اجرا با Docker

**فقط زیرساخت (توصیه‌شده برای توسعه):** `pnpm infra:up` یا `docker compose up -d`.

**کل پشته (API و وب داخل کانتینر):**

```bash
docker compose --profile app up -d --build
docker compose --profile app run --rm migrate pnpm prisma db seed   # داده نمونه (اختیاری)
```

- سرویس `migrate` پیش از API مایگریشن‌ها را اجرا می‌کند و API تا پایان موفق آن صبر می‌کند. وب پس از سالم شدن API بالا می‌آید.
- کانتینر API با `NODE_ENV=production` اجرا می‌شود و با اسرار ضعیف بالا **نمی‌آید**. پیش از اجرا در `.env` مقادیر زیر را تنظیم کنید:
  - `JWT_ACCESS_SECRET` با `openssl rand -base64 48`، `MEILI_MASTER_KEY` با `openssl rand -hex 24` و `APP_ENCRYPTION_KEY` با `openssl rand -base64 32`
  - `COOKIE_SECURE=true` (پشت HTTPS؛ مرورگرها `http://localhost` را امن حساب می‌کنند)
  - برای دمو محلی بدون درگاه واقعی: `PAYMENT_ALLOW_MOCK_IN_PRODUCTION=true`
- آدرس API برای rewrite های Next.js و `NEXT_PUBLIC_SITE_URL` هنگام **build** تصویر وب ثابت می‌شوند (build arg).
- تصاویر چندمرحله‌ای‌اند، با کاربر غیر root اجرا می‌شوند و healthcheck دارند. هدف `tools` در `apps/api/Dockerfile` برای مایگریشن و seed است.

## آزمون‌ها

```bash
pnpm test:unit          # بدون نیاز به سرویس
pnpm test:integration   # نیازمند PostgreSQL، Redis و (برای آزمون‌های جست‌وجو) Meilisearch
pnpm test               # همه
```

- **واحد:** موتور قیمت‌گذاری (کوپن درصدی/ثابت/ارسال رایگان، سقف، حداقل خرید، آستانه ارسال رایگان، مالیات داخل/خارج قیمت، گرد کردن)، ارث‌بری ویژگی‌ها در درخت دسته‌بندی، اعتبارسنجی مقادیر ویژگی با ارقام فارسی، Guard مجوزها، درگاه آزمایشی، diff ممیزی، رمزنگاری اسرار، محاسبه موجودی، تقویم تهران/جلالی. پکیج `shared` هم آزمون‌های نرمال‌سازی فارسی، اعتبارسنج‌ها و ماشین حالت سفارش را دارد.
- **یکپارچه:** کل اپ با همان pipeline تولید (`configureApp`) روی پایگاه‌داده واقعی بالا می‌آید: محاسبه قیمت در سرور و رد سفارش با مبلغ کهنه، **تسویه هم‌زمان ۸ مشتری برای ۳ عدد موجودی** (دقیقاً ۳ سفارش ثبت می‌شود)، تقسیم رزرو بین انبارها، idempotent بودن callback درگاه، تلاش مجدد پس از پرداخت ناموفق، انقضای سفارش و مهلت پرداخت در جریان، پرداخت یتیم، لغو و آزادسازی موجودی، سطح دسترسی هر نقش، چرخه ارسال/مرجوعی/بازپرداخت با ردپای ممیزی، بررسی Origin (CSRF)، چرخش و تشخیص استفاده مجدد refresh token، قفل حساب پس از تلاش‌های ناموفق، قوانین ویژگی‌های الزامی، مجوز تغییر قیمت، جست‌وجوی فارسی (ارقام، «ي/ك» عربی، نیم‌فاصله، SKU، مترادف، غلط تایپی، فیلتر ویژگی) و جایگزین پایگاه‌داده.
- آزمون‌های یکپارچه پایگاه‌داده‌ای به نام `*_test` را **از نو می‌سازند** (هر نام دیگری رد می‌شود)، از Redis db شماره ۱۵ و پیشوند نمایه `toolshop_test_` استفاده می‌کنند و به داده توسعه دست نمی‌زنند. در نبود Meilisearch آزمون‌های وابسته به آن skip می‌شوند.
- CI در [`.github/workflows/ci.yml`](.github/workflows/ci.yml) قالب‌بندی، build، lint، typecheck و همه آزمون‌ها را با سرویس‌های واقعی اجرا می‌کند.

## معماری و تصمیم‌های کلیدی

**مونولیت ماژولار.** هر دامنه یک ماژول Nest با سرویس‌های خودش است و ماژول‌ها فقط از راه سرویس‌های export‌شده یا رویدادهای دامنه با هم حرف می‌زنند. هیچ منطق تجاری در UI نیست؛ وب فقط API را صدا می‌زند و اسکیماهای zod مشترک را برای فرم‌ها به کار می‌برد.

**پول.** همه مبالغ به‌صورت عدد صحیح **ریال** در `BigInt` ذخیره و در API به عدد تبدیل می‌شوند؛ نمایش به تومان است (`displayCurrency` در تنظیمات). قیمت، تخفیف، هزینه ارسال و مالیات فقط در تابع خالص `calculateTotals` محاسبه می‌شوند؛ کلاینت قیمت نمی‌فرستد. هنگام ثبت سفارش، مبلغی که مشتری دیده (`expectedTotal`) با محاسبه سرور مقایسه می‌شود و در صورت تفاوت سفارش ثبت نمی‌شود (`CART_CHANGED`).

**موجودی.** برای هر تنوع و انبار `onHand` و `reserved` نگه داشته می‌شود و موجودی قابل فروش `onHand − reserved` است. ثبت سفارش ردیف‌ها را با `SELECT … FOR UPDATE` (به ترتیب ثابت برای جلوگیری از deadlock) قفل می‌کند و رزرو را به ترتیب اولویت انبارها تقسیم می‌کند؛ قید `CHECK (0 ≤ reserved ≤ onHand)` در پایگاه‌داده لایه دوم حفاظت است. پرداخت موفق رزرو را قطعی و از انبار کسر می‌کند، لغو یا انقضا آن را آزاد می‌کند و مرجوعی به همان انبار برمی‌گرداند. هر تغییر `onHand` یک ردیف تغییرناپذیر در دفتر `StockMovement` می‌سازد.

**سفارش.** ماشین حالت در `packages/shared` تعریف شده و فقط `OrdersService.transition` اثرهای جانبی (موجودی، کوپن، پرداخت، تاریخچه، رویداد) را اعمال می‌کند:

```
pending → awaiting_payment → paid → processing → packed → shipped → delivered
pending | awaiting_payment | paid | processing | packed  → cancelled → refunded
shipped | delivered                                     → returned  → refunded
```

سفارش پرداخت‌نشده پس از `STOCK_RESERVATION_TTL_MINUTES` با job تأخیری لغو می‌شود (یک sweeper دوره‌ای هم جاافتاده‌ها را می‌گیرد). اگر مشتری همان لحظه در صفحه بانک باشد، ۱۵ دقیقه مهلت اضافه داده می‌شود. ثبت کد رهگیری برای «ارسال‌شده» الزامی است و بازپرداخت فقط از بخش پرداخت‌ها و با ثبت تراکنش برگشت انجام می‌شود.

**پرداخت.** هر درگاه رابط `PaymentProvider` را پیاده می‌کند (`createPayment`، `verifyPayment`، `refundPayment`، `getPaymentStatus`، `parseCallback`) و `PaymentsService` مالک پایگاه‌داده و ماشین حالت است؛ پس تعویض PSP به منطق تجاری دست نمی‌زند. callback با قفل ردیف پرداخت idempotent است (تکرار callback اثر دوباره ندارد). پرداخت سفارشی که لغو شده تأیید (verify) نمی‌شود تا شاپرک تراکنش تأییدنشده را به مشتری برگرداند؛ اگر تأیید هم‌زمان با لغو انجام شده باشد، پرداخت برای بازپرداخت علامت‌گذاری و در ممیزی ثبت می‌شود. درگاه آزمایشی (`mock`) همین جریان redirect → callback → verify را شبیه‌سازی می‌کند و در production خاموش است.

**جست‌وجو.** هر تغییر محصول، قیمت یا موجودی در همان تراکنش یک رویداد در جدول `OutboxEvent` ثبت می‌کند؛ relay رویدادها را به BullMQ می‌دهد و worker سند جست‌وجو را به‌روز می‌کند (با صف dead-letter برای خطاها). متن‌ها پیش از نمایه‌سازی و هنگام جست‌وجو یکسان‌سازی می‌شوند: ارقام فارسی/عربی، «ي/ك»، اعراب و کشیده، نیم‌فاصله (هر دو شکل چسبیده و جدا نمایه می‌شوند). مترادف‌ها (مثل «هیلتی ← بتن‌کن»)، تحمل غلط تایپی (به‌جز اعداد)، جست‌وجوی SKU و مدل، فیلترهای پویا بر اساس ویژگی‌های دسته با شمارش disjunctive و مرتب‌سازی پشتیبانی می‌شوند. بازسازی کامل در نمایه موقت ساخته و سپس جابه‌جا (swap) می‌شود تا قطعی نداشته باشد. اگر Meilisearch در دسترس نباشد، جست‌وجو خودکار به پایگاه‌داده برمی‌گردد.

**ویژگی‌های پویا.** ویژگی‌ها (عدد با واحد، متن، بله/خیر، تک‌انتخابی، چندانتخابی) به دسته‌ها تخصیص داده می‌شوند و زیرشاخه‌ها آن‌ها را ارث می‌برند. مقادیر به‌صورت تایپ‌شده ذخیره می‌شوند (EAV با ستون‌های جدا برای هر نوع)، پس فیلتر و مقایسه دقیق است. پیش‌نویس می‌تواند ناقص باشد ولی انتشار بدون ویژگی‌های الزامی ممکن نیست.

**احراز هویت و دسترسی.** توکن دسترسی کوتاه‌عمر (JWT) و refresh token چرخشی در کوکی‌های httpOnly؛ refresh token فقط به‌صورت hash ذخیره می‌شود و استفاده مجدد از توکن قدیمی کل نشست را باطل می‌کند. رمزها با argon2id، محدودیت نرخ بر پایه Redis و قفل موقت حساب پس از ۸ تلاش ناموفق. ۴۴ مجوز ریز (مثل `product.price.update` جدا از `product.update`) در شش نقش سیستمی؛ نقش‌های جدید از پنل ساخته می‌شوند. هر کنترلر ادمین باید روی همه مسیرهایش `@RequirePermissions` داشته باشد و این هنگام شروع برنامه بررسی می‌شود؛ مسیری که فراموش شود اجازه بالا آمدن نمی‌دهد.

**ممیزی.** عملیات حساس (قیمت، موجودی، سفارش، پرداخت، نقش‌ها، تنظیمات و …) با کاربر، IP، User-Agent، شناسه درخواست و فقط فیلدهای تغییرکرده (قبل/بعد) ثبت می‌شوند.

**امنیت.** اعتبارسنجی zod روی همه ورودی‌ها، پاک‌سازی HTML توضیحات، بررسی نوع واقعی فایل آپلودی از روی محتوا، helmet، بررسی Origin برای درخواست‌های تغییردهنده (به‌جز callback درگاه)، کوکی SameSite، پیام‌های خطای فارسی با کد پایدار بدون نشت جزئیات داخلی، شناسه درخواست در لاگ و پاسخ خطا، اسرار رمزشده در پایگاه‌داده (AES-256-GCM)، و اعتبارسنجی پیکربندی production.

**سئو.** متادیتا و Open Graph و canonical برای هر صفحه، JSON-LD برای Product، BreadcrumbList و Organization، sitemap پویا و robots. صفحات کاتالوگ سمت سرور رندر می‌شوند و داده API با revalidate کش می‌شود.

**چرا `packages/shared` و نه `packages/types`؟** قراردادهای بین وب و API فقط نوع نیستند؛ اسکیماهای zod (اعتبارسنجی یکسان در فرم و سرور)، ماشین حالت سفارش، کاتالوگ مجوزها و ابزارهای متن فارسی هم مشترک‌اند. یک پکیج با خروجی ESM/CJS این‌ها را بدون تکرار نگه می‌دارد.

**چرا هنوز پکیج `integrations` و `ai` نیست؟** طبق اصل «بدون پیچیدگی زودهنگام»، تا وقتی مستندات رسمی ترب، دیجی‌کالا، ایتا، بله و PSP ها و قرارداد واقعی در دست نیست، endpoint ساختگی نوشته نشده است. نقاط اتصال آماده‌اند: رابط `PaymentProvider`، جدول `MarketplaceListing` و وضعیت همگام‌سازی آن در پنل محصول، رویدادهای Outbox برای همگام‌سازی، فیلدهای `aiSuggestedAnswer` و `aiConfidence` در پرسش‌ها، و `encryptSecret` برای نگهداری کلیدها. این پکیج‌ها در فاز ۲ و ۳ کنار این نقاط ساخته می‌شوند.

## افزودن درگاه پرداخت واقعی

1. یک کلاس در `apps/api/src/modules/payments/providers/` بسازید که `PaymentProvider` را پیاده کند (بر اساس مستندات رسمی PSP: ایجاد تراکنش، آدرس هدایت، تأیید با مبلغ ریالی، بازگشت وجه، استعلام).
2. آن را در `PAYMENT_PROVIDERS` در `payments.module.ts` ثبت کنید و مرچنت‌کد را از متغیر محیطی یا تنظیمات رمزشده بخوانید.
3. `PAYMENT_DEFAULT_PROVIDER` را به کد آن تغییر دهید. آدرس بازگشت `${APP_PUBLIC_URL}/api/v1/payments/callback/<code>` است و GET و POST را می‌پذیرد.
4. برای verify و callback آزمون یکپارچه بنویسید (الگو: `apps/api/test/integration/checkout.spec.ts`).

## پیش از استقرار در Production

- اسرار قوی (`JWT_ACCESS_SECRET`، `MEILI_MASTER_KEY`، `APP_ENCRYPTION_KEY`، رمز پایگاه‌داده) و `COOKIE_SECURE=true` پشت HTTPS.
- درگاه پرداخت واقعی (بالا) و حذف `PAYMENT_ALLOW_MOCK_IN_PRODUCTION`.
- `TRUST_PROXY_HOPS` برابر تعداد دقیق پراکسی‌ها، و عدم دسترسی مستقیم عمومی به پورت API (فقط از راه وب یا reverse proxy).
- `STORAGE_DRIVER=s3` برای چند نسخه‌ای بودن، پشتیبان‌گیری منظم PostgreSQL، و `maxmemory-policy noeviction` در Redis (صف‌ها).
- رمز مدیر ارشد را پس از اولین ورود عوض کنید؛ کاربران آزمایشی در production ساخته نمی‌شوند.
- جایگزینی placeholderها: نام و لوگو (`apps/web/src/config/site.ts` و `apps/web/src/styles/brand.css`)، اطلاعات حقوقی، نماد اینماد و مجوزها (پنل ← تنظیمات)، متن صفحات قوانین و حریم خصوصی.
- مقیاس افقی: چند نسخه API با `QUEUE_WORKERS_ENABLED=false` و یک یا چند نسخه worker.

## نقشه راه فاز ۲ و ۳

- **فاز ۲:** فاکتور و اسناد (PDF رسمی با اطلاعات حقوقی)، تیکت پشتیبانی، ورود با کد یکبارمصرف پیامکی (آداپتر سرویس پیامک)، اعلان‌ها (پیامک/ایمیل/ایتا/بله از روی رویدادهای Outbox)، خروجی ترب و همگام‌سازی دیجی‌کالا بر اساس مستندات رسمی، گزارش‌های فروش و انبار، ردیابی مرسوله.
- **فاز ۳:** مرکز هوش مصنوعی: پیشنهاد پاسخ به پرسش‌ها با تأیید انسانی (فیلدهای آماده)، تولید توضیحات و سئو، دسته‌بندی خودکار، جست‌وجوی معنایی. هوش مصنوعی هرگز SQL اجرا نمی‌کند و دسترسی مستقیم به پایگاه‌داده ندارد؛ فقط از راه سرویس‌های مجوزدار و با تأیید انسان برای عملیات حساس کار می‌کند.

## رفع اشکال

- **`Invalid environment configuration`:** پیام دقیقاً متغیر نامعتبر را نام می‌برد؛ `.env` را با `.env.example` مقایسه کنید.
- **جست‌وجو بدون فیلتر ویژگی یا نتایج قدیمی:** Meilisearch در دسترس نیست و جایگزین پایگاه‌داده فعال است؛ سرویس را بالا بیاورید و `pnpm search:reindex` را اجرا کنید.
- **ورود انجام می‌شود ولی نشست نمی‌ماند:** روی HTTP ساده `COOKIE_SECURE=false` باشد و سایت را از همان مبدأ `APP_PUBLIC_URL` باز کنید.
- **خطای پیدا نشدن کلاینت Prisma:** `pnpm build` (یا `pnpm db:generate`) را اجرا کنید.
- **آزمون یکپارچه پایگاه‌داده را رد می‌کند:** نام پایگاه‌داده `TEST_DATABASE_URL` باید به `_test` ختم شود و کاربر آن مجوز `CREATEDB` داشته باشد.
